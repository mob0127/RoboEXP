# Phase 0 工作总结：RoboEXP × kitchen-worlds 适配与 Scene Graph 构建

## RoboEXP 与 kitchen-worlds 的接口差异

**最终认识**

两套系统无法在环境层直接互换。RoboEXP 围绕 SAPIEN 2.x 的高保真光线追踪仿真与 FEG 飞行末端执行器设计，而 kitchen-worlds 基于 PyBullet 的 OpenGL 实时渲染与 PR2 移动操作平台构建。这种差异不仅体现在模拟器 API 上，更深层地影响了相机数据格式、机器人控制范式、渲染质量以及场景几何表达，导致 RoboEXP 的感知与记忆模块无法直接在 kitchen-worlds 中运行。

**关键差异与应对决策**

| 维度 | RoboEXP 原生设计 | kitchen-worlds 实际环境 | 适配策略 |
|------|----------------|----------------------|---------|
| 物理引擎 | SAPIEN 2.x，支持 GPU 光线追踪 | PyBullet，OpenGL 实时渲染 | 放弃 SAPIEN 环境层，在 PyBullet 上重建观测闭环 |
| 机器人 | FEG（六自由度末端位姿直接控制） | PR2（底盘平面移动 + 头部云台转动） | 以 PR2 为观测平台，重新设计视角采集策略 |
| 相机输出 | 字典索引的张量，OpenGL 坐标系 | 命名元组，需手动拆分通道 | 构建数据格式桥接层 |
| 渲染质量 | 高保真纹理，边缘清晰 | 低多边形，大尺度家具缺乏特征 | 视觉检测与物理引擎元数据注入双轨并行 |
| 场景知识 | 依赖在线视觉从零构建 | 加载时即知 URDF 结构与关节信息 | 部分利用 GT 信息弥补视觉盲区 |

## 环境适配层的构建

**最终成果**

构建了完整的 PyBullet 环境适配层，实现了 PR2 机器人在厨房场景中的可控多视角观测。PR2 能够沿平面移动底盘、调整头部俯仰角，在 13 个不同点位采集 RGB-D 图像与分割掩码。所有相机数据经转换后均可被 RoboEXP 的感知模块正常消费，GroundingDINO 与 SAM 在 GPU 上稳定推理，体素地图与实例记忆能够随观测增量更新。

**方法、问题与解决方案**

相机数据格式桥接是首批需要解决的问题。PyBullet 返回的相机数据为一个包含图像与深度信息的扁平元组，而 RoboEXP 期望的是按相机索引组织的字典结构，且深度尺度与坐标系约定不同。通过建立一个轻量转换层，将元组拆分为 RGB、深度、分割三个通道，调整深度值量纲，并按目标格式重组，实现了两个系统之间的数据贯通。

PR2 的集成是适配层工作的核心难点，其中底盘移动问题最为棘手。最初尝试直接重置 PR2 的底盘位姿来实现移动，但机器人身体频繁穿透家具。深入排查后发现，PR2 在 PyBullet 中的本体结构依赖底盘关节组维持内部一致性：底盘的平面三自由度由特定关节索引管理，直接修改 body origin 会导致关节坐标与连杆位姿计算脱节，从而引发全身连杆坐标系的连锁错乱。修复方式改为通过底盘关节组配置来驱动位姿变化，使机器人全身位姿保持同步，彻底消除了穿模现象。

头部相机的控制与追踪也经历了一段调整期。PR2 头部具备水平旋转与俯仰两个关节，通过配置头部关节组即可改变视角方向。但早期曾错误地将某个前臂连杆当作相机参考系，导致头部转动在图像中没有体现。经过对 PR2 URDF 链路结构的逐层核对，确认了相机光学帧的实际挂载位置，并验证了头部俯仰角变化能够通过关节链正确传播到相机位姿。在场景观测中，为覆盖从台面到橱柜的不同高度区域，最终设计了从向下约六十三度到向上约二十三度的俯仰范围，充分利用了 PR2 头部云台的硬件极限。

运行环境层面还遇到了两类突发故障。一是 GPU 计算缓存损坏导致 PyTorch 无法初始化 CUDA 上下文，表现为所有涉及 CUDA 的操作均报未知错误。通过清除 NVIDIA 运行时缓存重建上下文，GPU 推理恢复正常，运行时间从 CPU 模式的五至六分钟缩短到一至两分钟。二是 GroundingDINO 的文本编码器在离线环境下尝试联网下载配置文件，导致加载超时。通过强制启用离线模式，系统转而使用本地缓存的模型文件，绕过了网络依赖。

下表汇总了最终采用的 13 个观察点位配置：

| 视角类别 | 底盘位置 | 头部俯仰 | 观测目标 |
|---------|---------|---------|---------|
| 正面 countertop | x=1.8~2.0，y=0 | 0.2~0.3（俯视 11°~17°） | 台面物体 |
| 侧方覆盖 | x=1.8，y=±0.6~0.8 | 0.3~0.5 | 台面边缘 |
| 远距离全局 | x=2.2~2.5，y=0 | 0.2~0.8 | 全局布局 |
| 仰视橱柜 | x=1.5，y=0~±0.6 | -0.4~-0.1（仰视 20°~23°） | 高处橱柜、搁架 |
| 极限俯视 | x=2.0~2.5，y=0~±0.5 | 0.6~1.1（俯视 34°~63°） | 尝试观察 countertop 下方 |

## 较完整 Scene Graph 的构建流程

**最终成果**

从空场景出发，成功构建了一个包含约二十个节点的 ActionSceneGraph。图中节点由三类信息融合而成：视觉检测得到的台面小物体、从物理引擎注入的大型家具、以及从关节信息注入的操作把手。场景图还包含了经过验证的 inside 关系——抽屉打开后，瓶子与合成苹果均通过 open 动作节点正确关联到橱柜内部空间。整个场景图支持序列化为 JSON 与 pickle，可通过 Graphviz 渲染为可视化有向图，并生成了包含全局视角、机器人视角与实时信息面板的演示视频。

**方法、问题与解决方案**

多视角观测是构建完整场景图的基础。初始仅设置四个观察点位，但检测到的物体数量与类别十分有限。为此逐步扩展至十三个点位，覆盖厨房正面、左右侧方、远距离全局，以及专门抬头观察橱柜的仰视角和极限俯视台面下方的低角度。视角扩展后，视觉检测从四种物体增加到七种，新增了锅具、碗、抽屉等类别。然而，大型固定家具——烤箱、洗碗机、橱柜、搁架、微波炉——几乎从未被视觉模型检出。这源于 PyBullet 低多边形渲染缺乏真实纹理与边缘特征，且烤箱和洗碗机从任何正面视角都被 countertop 结构物理遮挡。这一发现说明，在现有仿真平台下，纯粹依赖视觉从零构建完整场景图存在结构性盲区。

针对大型家具的视觉盲区，采用了物理引擎元数据注入策略。直接从 PyBullet 世界对象中提取台面、橱柜、微波炉、烤箱、洗碗机、搁架的几何包围盒，在其表面采样体素点，作为带标签的合成实例注入记忆系统。这些节点具备完整的三维空间范围，可被后续空间推理直接利用。注入后场景图从仅有几个台面小物件，扩展为包含全部主要家具的完整空间结构。需要诚实指出的是，这一手段本质上是用仿真器的先验知识补足了视觉算法的短板，验证了场景图的数据结构能力，但并未验证视觉模型本身对大尺度家具的检测能力。

操作把手的处理遵循了类似逻辑。视觉检测对细小把手极不稳定，图像分辨率与渲染质量共同导致其经常漏检。但由于 kitchen-worlds 中所有可开合部件均基于 PyBullet 关节构建，因此直接从关节信息中提取把手位置、运动类型——旋转门或平移抽屉——以及父级家具体，在场景图中创建对应的把手节点并标记运动方向与开合极限。共注入八个把手节点，全部正确关联到各自的父家具。

Inside 关系的验证分为两个阶段。第一阶段使用合成物体：将抽屉打开至极限位置的八成后，在其内部空间直接生成一个体素级别的苹果实例，手动将其挂到 open 动作节点下，建立了 apple inside cabinet 的关系链路，验证了场景图对容器-内容物关系的表达能力。第二阶段使用真实物体：将 countertop 上的瓶子通过物理引擎移入抽屉内部，然后重新观测。由于抽屉前面板遮挡以及 PR2 的身高限制，头部相机无法直接看到抽屉内部的瓶子，视觉检测自然无法生成 inside 关系。对此采取的 Fallback 策略是读取瓶子的物理引擎位置，确认其落入抽屉包围盒内部后，直接在该位置创建体素实例并建立 inside 关系。这一流程证明了在视觉不可达的情况下，系统仍能借助物理一致性维持正确的空间关系，但也暴露了当前闭环的缺陷：inside 关系并非由视觉确认，而是由物理位置推断。

在生成演示视频后，进一步发现了机器人穿模与相机视角异常的问题。视频显示 PR2 初始位置过于靠近 countertop，且移动过程中身体穿透家具，导致相机多次拍到物体内部而非场景表面。修复后重新评估发现：即使穿模问题解决、所有视角均调整到家具前方，烤箱与洗碗机仍然受 countertop 物理结构遮挡而无法被任何视角看到；橱柜与搁架虽已进入相机视野，但 GroundingDINO 仍不能将其识别为对应类别。这进一步证明，GT 家具注入不是临时补丁，而是在当前渲染质量下维持场景图完整性的必要设计。

最终的演示视频综合展示了整个建图过程：左侧为固定全局视角，能看到 PR2 背面与厨房全景；右侧上方为机器人头部相机实时画面，下方为动态滚动的信息面板，用颜色区分普通物体与把手，并实时列出当前观测到的依附关系。视频时长约 42 秒，完整覆盖了从空场景到最终二十节点场景图的构建全过程。

## 当前缺漏与诚实反思

尽管 Phase 0 在结构验证层面达到了预期目标，但以下缺漏需要坦率指出，它们直接影响后续阶段的可行性评估。

1. **大型家具节点完全绕过了视觉感知。** 当前场景图中的 countertop、oven、dishwasher、microwave、shelf、cabinet 均来自物理引擎的直接注入，而非 GroundingDINO 的视觉检测。这意味着系统并未实现真正意义上的"从零开始"自主建图，而是在关键骨架节点上借用了仿真器的先验信息。若迁移到一个视觉模型从未见过的新环境，这些节点将无法自动生成。

2. **Inside 关系未形成视觉闭环。** 抽屉打开后，相机因几何遮挡无法直接观测内部，当前 inside 关系依赖物理位置回退或人工合成。在真实机器人系统中，容器内部的发现应当由视觉触发——即在抽屉拉出的瞬间，深度图出现新的点云簇，进而被分割为新实例并自动关联到容器节点。当前的 Fallback 策略虽然验证了数据结构，但未实现这种动态发现机制。

3. **视角覆盖存在平台级物理极限。** PR2 头部俯仰关节的最大仰角约为二十七度，从地面位置只能看到橱柜底部边缘，无法完整覆盖高处空间。即使增加更多观察点位，只要机器人基座保持在地面，橱柜顶部与高处搁架就难以被完整观测。这限制了场景图在高处区域的视觉完备性，如需突破需引入登高、蹲下或额外相机等硬件变更。

4. **未涉及真实抓取与运动规划。** 当前所有物体的空间移动均通过直接重置物理位姿完成，没有调用逆运动学求解器，也没有使用 PR2 的双臂执行真实的 pick-place 操作。Scene Graph 目前只是一个静态观测产物，尚未与 TAMP 规划器的执行层形成闭环。这是 Phase 1 需要解决的核心任务。

5. **部分把手的父节点匹配仍不完整。** 少量把手因父物体类别未在场景图中创建对应节点，导致注入时被跳过。这表明场景图实例的全集与 PyBullet 关节的父级引用之间还存在覆盖缺口，需要在后续阶段完善物体类别映射表，或扩展视觉检测的类别字典。

这些缺漏决定了 Phase 0 的定位：它验证了 RoboEXP 的感知-记忆-场景图算法能够在 PyBullet 环境中运行，并能通过多源信息融合构建出结构正确的场景图，但它尚未实现一个完全自主、纯视觉驱动、可闭环操作的建图系统。
